# 养殖场监测产品端到端发布计划

## 1. 发布目标

本次发布目标是把当前仓库收口成一个可验收的程序产品，而不是单独完成网站原型。

目标交付链路：

`PC 采集端 -> 协议上传 -> 平台接收与入库 -> Web 可视化 -> 自动化验收`

## 2. 本轮范围

### 2.1 必须完成

- `PC` 采集端可以稳定生成并发送监测报文
- 平台后端可以接收、解析、记录、入库并返回应答
- Web 端可以查看基础档案、实时数据、协议日志、告警和巡检
- 自动化测试可以覆盖平台回归和端到端关键路径

### 2.2 可以延后

- 复杂报表导出
- 多租户权限细分
- 外部短信/微信通知
- 复杂设备控制下发
- 高并发和分布式部署

### 2.3 适合逐步追加的成熟化功能

在主链路稳定后，可以优先考虑追加以下功能，让产品更像正式可用的软件，而不只是联调样品：

- 运行状态看板：集中展示最近上传、最近异常、最近告警、最近巡检
- 全局搜索与筛选：按养殖场、设备、时间快速定位问题
- 设备离线提醒与数据中断提示
- 简单的操作留痕：谁确认了告警、谁提交了巡检、最近何时有数据
- 一键验收工具入口：降低演示和交付门槛
- 运维帮助区：快速判断“PC 没发、平台没收、解析失败、页面没展示”

## 3. 协作者分工

### 3.1 平台开发程序员 `019f26d1-0276-7f33-b77a-29641bec570e`

负责范围：

- 平台后端接口
- 平台 TCP 接收服务
- Web 管理端页面
- 协议日志与联调可观测性

本轮重点结果：

- 平台能够明确识别 `PC` 上传来源
- 接收日志可以展示原始报文、解析状态、指标数量、平台应答
- Web 端可以支撑最终演示和验收

### 3.2 PC 软件开发程序员 `019f3501-6159-7d91-a494-899dec8911a9`

负责范围：

- `PC` 采集端采集与上传
- 长连接、重连、超时和本地待上传任务机制
- 协议报文正确性
- 本地设备因子和平台协议字段对齐

本轮重点结果：

- 能稳定向平台发送正确报文
- 正常发送后不主动断开
- 只有在服务端断联或异常时才重连
- 具备可演示的发送状态与联调日志

### 3.3 自动化测试工程师 `019f357b-69b6-70b0-a434-26a3e23f4a00`

负责范围：

- 后端回归测试
- 前端回归测试
- 协议上传测试
- 端到端验收脚本和结果报告

本轮重点结果：

- 给出最终验收测试清单
- 覆盖 `PC -> 平台 -> Web` 核心链路
- 稳定输出失败归因，区分平台问题和 PC 问题

## 4. 业务补充要求

为了让产品可验收，本轮补充以下业务要求：

1. 平台必须把“协议上传”从隐藏技术能力提升为可见业务能力。
2. `PC` 端必须是本轮交付的一部分，不能只保留“未来预留”。
3. 演示环境必须允许在无真实硬件情况下，用模拟采集完成一轮完整联调。
4. 联调失败时必须能定位到是 `PC` 未发送、平台未接收、协议解析失败，还是 Web 未展示。
5. 验收必须用固定剧本执行，避免“今天能演、明天不能演”。

## 5. 最终验收剧本

### 5.1 启动

1. 启动 `MySQL`
2. 启动平台后端
3. 启动平台 Web 前端
4. 启动平台 TCP 接收服务
5. 启动 `PC` 采集端

### 5.2 联调

1. 在 `PC` 端触发一次采集或模拟采集
2. 确认 `PC` 端显示发送成功或进入稳定连接状态
3. 在平台协议日志页确认收到原始报文与平台应答
4. 在实时监测页确认最新数据刷新
5. 如超过阈值，在告警中心确认告警出现

### 5.3 回归

1. 登录平台
2. 查看总览首页
3. 查看设备和传感器信息
4. 新增或查看巡检记录
5. 运行自动化测试并记录结果

## 6. 验收标准

- `PC` 端存在可演示的发送链路，而不是仅靠脚本代替
- 平台可接收到至少一条来自 `PC` 端的真实测试报文
- Web 页面对该次报文和监测数据可见
- 自动化测试可以验证关键路径且结果可复现
- 出现失败时，日志足以定位责任环节
