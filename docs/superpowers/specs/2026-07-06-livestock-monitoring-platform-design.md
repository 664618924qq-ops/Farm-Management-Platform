# 养殖场数据监测平台设计说明

## 1. 项目概述

本项目用于建设一套面向养殖场景的综合型数据监测平台，第一版以环境类数据监测为主，覆盖多养殖场、多栋舍的管理与监测需求。

平台将服务两类主要用户：

- 场长/老板：查看多场区总览、告警、趋势和报表
- 现场员工：查看设备状态、处理告警、填写巡检记录

系统不仅要为 `PC` 采集工具预留接口，还要把 `PC` 采集端纳入本轮交付，使现场传感器采集数据能够通过 `TCP` 协议上传到平台接收端，再进入平台数据库和监测页面。

## 2. 第一版目标

第一版目标不是一次做成所有功能，而是先交付一个可验收的端到端产品，跑通从 `PC` 采集、平台接收到 Web 展示的最小可用闭环。

第一版需要完成：

- 多养殖场、多栋舍基础档案管理
- 用户登录与角色权限
- 设备与传感器管理
- 实时环境数据展示
- 历史趋势查询
- 站内告警与处理
- 巡检记录管理
- `TCP` 数据接收与入库
- `PC` 采集端联调能力
- 模拟上传联调能力

第一版暂不完成：

- 短信或微信真实发送
- 真实硬件驱动接入
- 复杂报表导出
- 自动控制设备下发
- 高并发分布式拆分部署

## 4. 总体架构

系统按以下链路工作：

`传感器 -> PC 采集工具 -> TCP 上传 -> 平台接收模块 -> MySQL -> Web 平台页面`

第一版不再只开发网站平台，而是同时收口 `PC` 采集端、平台接收端和 Web 页面。后端仍需保留单独的接收模块边界，避免后续继续扩展真实设备时重构核心业务。

### 4.1 系统模块

平台第一版包含以下模块：

1. `Web 前端模块`
   提供登录、总览、实时监测、趋势图、告警中心、设备管理、巡检记录等页面。

2. `业务 API 模块`
   提供养殖场、栋舍、设备、传感器、监测数据、告警、巡检、用户权限等接口。

3. `TCP 数据接收模块`
   负责接收来自 `PC` 工具的数据报文，完成解析、校验、基础防重和入库。

4. `数据库持久化模块`
   存储基础档案、实时数据、历史数据、告警、巡检与用户信息。

5. `PC 采集端模块`
   负责采集或模拟采集现场数据、维持上传连接、处理应答和补传，并为演示环境提供可联调入口。

6. `模拟上传模块`
   在真实硬件尚未接入前，用于模拟上传传感器数据，验证整条链路。

## 5. 用户角色与权限

第一版角色控制先保持简单，只分为两类。

### 5.1 管理员/场长

权限范围：

- 查看所有养殖场与栋舍
- 查看总览、趋势、告警
- 管理设备与传感器
- 查看和审核巡检记录
- 管理告警状态

### 5.2 员工

权限范围：

- 查看分配范围内的养殖场/栋舍数据
- 查看设备状态和实时数据
- 处理告警确认
- 新增和查看巡检记录

## 6. 核心业务对象

第一版平台核心对象如下：

### 6.1 养殖场

用于表示一个实际经营场区。

关键字段：

- 编码
- 名称
- 联系人
- 联系电话
- 地址
- 状态

### 6.2 栋舍

用于表示养殖场下的具体栋舍或区域。

关键字段：

- 所属养殖场
- 栋舍编码
- 栋舍名称
- 类型
- 状态

### 6.3 设备

用于表示连接数据来源的采集设备或网关设备。

关键字段：

- 所属养殖场
- 所属栋舍
- 设备编码
- 设备名称
- 设备类型
- 协议类型
- 连接方式
- 在线状态
- 通讯配置

### 6.4 传感器

用于表示设备上的具体测点定义。

关键字段：

- 所属设备
- 指标编码
- 指标名称
- 单位
- 下限
- 上限
- 排序

### 6.5 实时数据

用于保存每个传感器最新一次有效数据，便于首页和监测页面快速读取。

### 6.6 历史数据

用于保存完整时间序列，用于趋势图、追溯和后续报表。

### 6.7 告警记录

用于记录阈值越限、设备离线、上传失败等异常事件。

### 6.8 巡检记录

用于记录员工现场检查、备注和处理过程。

### 6.9 用户

用于登录和权限控制。

## 7. 第一版监测指标

第一版以环境类指标为主，默认先支持以下指标：

- 温度
- 湿度
- 氨气
- 二氧化碳
- 光照

这些指标会作为第一版的默认传感器类型进入系统设计。后续如果需要增加其他环境指标，可以通过传感器配置扩展，而不改整体架构。

## 8. 页面设计范围

### 8.1 登录页

用于账号登录和进入平台。

### 8.2 总览首页

面向管理员/场长，展示：

- 多养殖场总体状态
- 今日告警数量
- 在线设备数量
- 关键指标卡片
- 主要趋势图

### 8.3 实时监测页

按养殖场和栋舍查看实时数据，包括：

- 当前指标值
- 状态颜色
- 设备在线状态
- 最近更新时间

### 8.4 历史趋势页

按指标、时间范围查看折线图和历史记录。

### 8.5 设备管理页

管理设备基础信息、通讯配置和所属关系。

### 8.6 传感器管理页

管理传感器指标、单位、阈值和排序。

### 8.7 告警中心

展示当前活动告警、历史告警和处理状态。

### 8.8 巡检记录页

供员工提交巡检内容，也供管理者查看。

## 9. 告警设计

第一版告警先以内站告警为主，并预留外部通知扩展字段。

### 9.1 告警类型

- 阈值越限告警
- 设备离线告警
- 数据异常告警
- 上传失败告警

### 9.2 告警生命周期

- 触发
- 恢复
- 确认
- 关闭

### 9.3 外部通知预留

第一版不真正发送短信或微信，但数据库和服务层需要预留以下能力：

- 通知渠道字段
- 通知状态字段
- 通知失败原因字段

## 10. TCP 接收设计

第一版默认由 `PC` 工具上传真实测试数据，平台需要同时具备接收能力、日志能力和联调定位能力。

### 10.1 接收目标

平台接收模块负责：

- 监听指定 `TCP` 端口
- 接收文本或 `JSON` 报文
- 校验设备身份
- 校验字段完整性
- 解析监测指标
- 写入实时数据和历史数据
- 触发告警判断

### 10.2 第一版报文建议

第一版建议使用 `JSON` 文本报文，便于联调和排错，示例：

```json
{
  "farmCode": "FARM-001",
  "shedCode": "SHED-001",
  "deviceCode": "DEV-001",
  "reportedAt": "2026-07-06T10:00:00+08:00",
  "metrics": [
    { "code": "temperature", "value": 28.5, "unit": "C" },
    { "code": "humidity", "value": 71.2, "unit": "%" },
    { "code": "ammonia", "value": 8.1, "unit": "ppm" },
    { "code": "co2", "value": 650.0, "unit": "ppm" },
    { "code": "illumination", "value": 320.0, "unit": "lx" }
  ]
}
```

### 10.3 未来扩展要求

`PC` 工具在本轮即会参与交付，但仍需要为后续升级预留：

- 身份鉴权
- 心跳机制
- 断线重连
- 离线补传
- 报文签名
- 重复报文防重

## 11. 数据存储设计原则

第一版采用 `MySQL` 即可，不引入额外数据库。

存储原则如下：

- 基础档案和业务数据全部入 `MySQL`
- 实时数据和历史数据分开存储
- 重要查询字段建立索引
- 告警记录保留完整状态变更信息

如果后续实时压力增大，再考虑引入缓存或时序优化方案。

## 12. 与参考 PC 项目的关系

你提供的参考项目 `D:\pamGo\个人\codex项目\养虾监测工具` 已经体现了几个可复用思路：

- 设备与测点分离建模
- 本地采集与平台上传职责分离
- 上传任务和告警作为独立业务对象
- 适配器式设备接入思路

本平台第一版会参考其结构经验，并把 `PC` 端作为正式交付的一部分推进，保证平台字段、协议报文和联调流程方向一致。

### 13.2 可扩展性

## 14. 第一版实施顺序

建议开发顺序如下：

1. 创建前后端工程骨架
2. 完成后端数据库模型与基础接口
3. 完成前端登录与整体布局
4. 完成养殖场、栋舍、设备、传感器管理
5. 完成实时数据与历史趋势页面
6. 完成告警中心与巡检记录
7. 完成 `PC` 采集端与平台接收端联调
8. 完成 `TCP` 接收、协议日志和模拟上传联调
9. 完成部署文档、启动说明和验收剧本

## 15. 设计结论

第一版推荐以 `Vue 3 + FastAPI + MySQL + PC 采集端` 为核心，优先跑通“本地采集/模拟采集 + 数据接收 + 监测展示 + 告警处理”的完整闭环。

这样既适合快速落地，也便于你在开发过程中逐步理解：

- 前端页面是怎么组织的
- 后端接口是怎么提供的
- 数据库表是怎么设计的
- 传感器数据是怎么进入平台并展示的

后续再继续扩展真实硬件采集能力和更复杂的运维场景，就会顺很多。
