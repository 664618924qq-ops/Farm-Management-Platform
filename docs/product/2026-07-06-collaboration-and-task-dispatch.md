# 养殖场监测产品协作与任务调度机制

## 1. 目的

这份文档用于固定当前项目的协作方式，避免任务安排只靠临时沟通。

本机制适用于以下三类协作者：

- 平台开发程序员 `019f26d1-0276-7f33-b77a-29641bec570e`
- PC 软件开发程序员 `019f3501-6159-7d91-a494-899dec8911a9`
- 自动化测试工程师 `019f357b-69b6-70b0-a434-26a3e23f4a00`

最终原则只有一个：所有协作都服务于最终验收，而不是局部最优。

## 2. 角色划分

### 2.1 产品负责人

由当前主线程负责统一协调，职责包括：

- 定义阶段目标
- 收集各协作者进展、想法、风险和建议
- 做产品取舍和优先级判断
- 下发下一轮任务
- 对最终验收结果负责

### 2.2 协作者

各协作者负责各自工作面的实现与反馈，但不单独决定产品方向。协作者可以提出优化想法、风险提醒和替代方案，最终是否纳入下一轮，由产品负责人统一决定。

## 3. 例会节奏

当前采用两种触发方式并行：

### 3.1 定时例会

- 每 `10` 分钟组织一次产品协调例会
- 例会关注四件事：
  - 当前进展
  - 当前风险
  - 下一轮最值得做的事情
  - 哪些新功能值得纳入产品，能让成品更成熟

### 3.2 事件触发

即使未到 `10` 分钟，只要出现以下情况，也可以立即进入下一轮任务安排：

- 某协作者完成了一轮关键工作
- 某协作者被阻塞
- 平台、PC、测试之间出现依赖冲突
- 出现明显影响最终验收的新风险
- 出现明显提高验收成功率的优化想法
- 出现明显能提升产品成熟度且不会破坏当前主链路的新功能机会

## 4. 下一轮任务何时下发

下一轮任务不是机械定时下发，而是按以下规则执行：

1. 定时例会开始时，读取三位协作者的最新状态
2. 判断是否需要调整优先级
3. 额外判断是否存在值得推进的新功能候选
4. 如果方向不变，则只补充最关键的下一步
5. 如果发现新的高优先级风险，则立即改派任务
6. 每位协作者每轮只接收 `1` 到 `3` 个最高价值任务

这样做的原因：

- 避免任务切换过于频繁
- 避免大家各做各的
- 避免低价值优化挤占主链路时间
- 让产品负责人持续经营产品成熟度，而不是只被动盯缺陷

## 5. 产品取舍原则

每次例会收集到的想法，不会平均采纳，而是按以下顺序判断：

1. 是否直接影响最终验收
2. 是否直接影响 `PC -> 平台 -> Web` 主链路
3. 是否能提高演示稳定性
4. 是否能提高问题定位效率
5. 是否能让产品从“能演示”升级到“更像正式产品”
6. 是否只是锦上添花

只有排在前面的事项，才会进入下一轮任务。

以下内容默认优先级较低：

- 纯视觉修饰
- 非关键页面的小优化
- 不影响验收的结构重构
- 暂时无验证价值的扩展功能

## 5.1 新功能挖掘原则

产品负责人需要主动思考哪些功能适合在当前阶段增加，而不是只等待协作者提建议。

优先考虑以下类型的新功能：

- 能明显提升用户对系统“可管理、可追踪、可操作”感知的功能
- 能补齐从演示产品走向正式产品的关键空白
- 不会破坏当前 `PC -> 平台 -> Web` 主链路稳定性的轻量增强
- 能被快速验证、快速讲清楚价值的功能

当前阶段优先挖掘的成熟化方向包括：

- 联调与运行状态可视化
- 数据异常与设备异常的运营提示
- 关键对象的筛选、搜索、最近操作记录
- 验收友好的状态看板和操作引导
- 简单但高价值的运维工具入口

## 6. 协作者回报格式

每轮例会默认要求协作者按简短格式回报，不写长报告。

建议回报结构：

1. 当前最稳定、最适合最终演示的能力
2. 当前最大的产品缺口
3. 最建议补的 `1` 到 `2` 个优化
4. 需要其他协作者如何配合

## 7. 任务下发原则

给协作者下发任务时，遵循以下规则：

- 一轮只下发最重要的 `1` 到 `3` 个任务
- 任务必须服务于当前验收目标
- 任务描述必须明确，不发空泛方向
- 新任务要尽量避免打断正在收尾的高价值工作
- 发现错误方向时，允许立即中断并改派

## 8. 当前项目的优先级口径

当前项目的统一优先级如下：

1. 打通 `PC -> 平台 -> Web` 主链路
2. 保证联调过程稳定、可重复
3. 保证协议日志、实时监测和验收页面可见
4. 保证自动化测试能支撑最终验收
5. 在以上稳定后，优先增加能显著提升产品成熟度的新功能
6. 最后再做一般体验优化

## 9. 会议产出要求

每次例会结束后，产品负责人应输出一段简短结论，至少包含：

- 本轮会议结论
- 采纳了哪些优化想法
- 采纳了哪些适合新增的功能方向
- 放弃了哪些建议以及原因
- 各协作者的下一轮任务

同时，每次例会必须追加更新 [项目进度留痕](C:/Users/DELL/Documents/Codex%20project/docs/product/progress-log.md)，不能只覆盖 README 或其他说明文档。

每条留痕至少包含：

- 记录时间
- 本轮参与线程和响应情况
- 当前进度
- 当前问题或风险
- 产品负责人决策
- 已下发任务
- 下一步安排

## 10. 生效方式

本机制从文档落地后立即生效，并与当前自动化协调机制配合执行。

如果后续项目节奏变化，可以更新本文件，但默认规则保持不变：

- 每 `10` 分钟一次定时协调
- 关键事件提前触发
- 产品负责人统一拍板
- 每轮协调都追加进度留痕，不覆盖历史
